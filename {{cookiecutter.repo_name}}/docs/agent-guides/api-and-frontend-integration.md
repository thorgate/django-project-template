# API & Frontend Integration

## CamelCase Convention

The API uses camelCase for all JSON keys. This is handled automatically by three components:

1. **CamelCaseJSONRenderer** — converts snake_case Python dict keys to camelCase in responses
2. **CamelCaseJSONParser** — converts camelCase JSON keys to snake_case when parsing requests
3. **CamelCaseMiddleWare** — converts camelCase query parameters to snake_case

**What this means for writing code:**
- Write all Python code in snake_case as normal
- API consumers send/receive camelCase JSON
- Filter parameters in URLs are also camelCase (e.g. `?pageNumber=2&pageSize=10&sort=creationTimeDesc`)
- The `SPECTACULAR_SETTINGS` includes `CAMELIZE_NAMES: True` and the camelCase postprocessing hook, so the OpenAPI schema also uses camelCase

## Pagination Response Shape

All list endpoints return paginated responses with this structure:

```json
{
  "totalCount": 42,
  "nextUrl": "http://localhost:8000/api/documents/?pageNumber=3&pageSize=10",
  "next": {
    "pageNumber": ["3"],
    "pageSize": ["10"]
  },
  "previousUrl": "http://localhost:8000/api/documents/?pageNumber=1&pageSize=10",
  "previous": {
    "pageNumber": ["1"],
    "pageSize": ["10"]
  },
  "current": {
    "pageNumber": 2,
    "pageSize": 10
  },
  "results": [...]
}
```

**Query parameters:**
- `pageNumber` (or `page_number`) — page number, default 1
- `pageSize` (or `page_size`) — items per page, default 10

**Notes:**
- `next`/`previous` are parsed query objects (not raw URLs) — `null` when there's no next/previous page
- `nextUrl`/`previousUrl` are the raw URL strings
- `current` always contains the current page number and page size as integers

## Authentication Flow (Backend)

### JWT Endpoints

| Endpoint | Method | Purpose |
|----------|--------|---------|
| `/api/auth/token/` | POST | Obtain token pair (email + password -> access + refresh) |
| `/api/auth/token/refresh/` | POST | Refresh access token (refresh token -> new access + new refresh) |
| `/api/auth/token/verify/` | POST | Verify a token is valid |
| `/api/user/signup` | POST | Register new user (returns token pair) |
| `/api/user/me` | GET/PUT | Current user details |
| `/api/user/forgot_password` | POST | Initiate password recovery |
| `/api/user/forgot_password/token` | POST | Complete password recovery |

### Token Configuration (from `settings/base.py`)

- **Access token lifetime**: `DJANGO_JWT_MAX_AGE` env var, default 5 minutes
- **Refresh token lifetime**: 7 days
- **Rotate refresh tokens**: enabled (each refresh returns a new refresh token)
- **Algorithm**: HS256 by default; RS256 if `DJANGO_JWT_PRIVATE_KEY` and `DJANGO_JWT_PUBLIC_KEY` are set
- **Auth header**: `Authorization: Bearer <token>`

### Authentication in Tests

Test settings (`settings/test.py`) swap JWT for `SessionAuthentication`:
```python
REST_FRAMEWORK["DEFAULT_AUTHENTICATION_CLASSES"] = (
    "rest_framework.authentication.SessionAuthentication",
)
```

Authenticate in tests using `force_login`:
```python
def test_my_endpoint(django_client, user):
    django_client.force_login(user)
    response = django_client.get("/api/documents/")
    assert response.status_code == 200
```

## OpenAPI Schema

Generated by **drf-spectacular**. Key configuration in `settings/base.py`:

- `DEFAULT_SCHEMA_CLASS`: `drf_spectacular.openapi.AutoSchema` (globally configured in REST_FRAMEWORK)
- Custom `AutoSchema` in `{{cookiecutter.default_django_app}}/rest/{{cookiecutter.default_django_app}}/schema_generator.py` — integrates `ForRequestSchemaSerializerMixin` to generate clean request schemas (strips read-only fields)
- Schema endpoint: `/api/schema/` (JSON)
- Swagger UI: `/api/schema/swagger-ui/`
- ReDoc: `/api/schema/redoc/`
- Schema path prefix: `/api/`
- Camelized field names and postprocessing hook enabled

**Export commands:**
- `make export-schema` — exports schema to `{{cookiecutter.django_folder_name}}/schema.json` and copies to `app/lib/queries/schema.json`

## RTK Query Pipeline (Stub)

The frontend API client is auto-generated from the OpenAPI schema:

1. `make export-schema` — export OpenAPI JSON from Django
2. `make generate-rtk-query-api` — runs export + generates TypeScript API client + applies patches + formats

**Key files:**
- `app/lib/queries/schema.json` — OpenAPI schema copy
- `app/lib/queries/queriesApi.generated.base.ts` — unpatched generated code (do NOT edit)
- `app/lib/queries/queriesApi.generated.ts` — patched generated code
- `app/lib/queries/queriesApi.generated.patch` — patch file for customizations

**To customize generated code:**
1. Edit `queriesApi.generated.ts`
2. Run `make create-rtk-queries-api-patch` to save your changes as a patch
3. Future regenerations will auto-apply the patch

## i18n Namespace Conventions

Translation extraction (`make extract-i18n` / `pnpm extract-i18n`) uses `i18next-scanner`, which performs **static text extraction** — it cannot trace which `t` function came from which `useTranslation()` call. All keys without an explicit namespace prefix are assigned to the `defaultNs` (`"common"`), polluting `common.json` with keys that belong to other namespaces.

**Rule: Always use namespace-prefixed keys in `t()` calls.**

```tsx
// WRONG — scanner puts "columns.name" into common.json
const { t } = useTranslation("myFeature");
t("columns.name");

// CORRECT — scanner routes to myFeature.json via the ":" nsSeparator
const { t } = useTranslation(["myFeature", "common"]);
t("myFeature:columns.name");
```

**Guidelines:**
- Pass namespaces as an **array** to `useTranslation()` — include `"common"` if the component also uses common keys
- **Always prefix** the key with `namespace:` in every `t()` call, even for the first namespace in the array
- When adding a new namespace: add it to `scanner.config.js` `ns` array, `types/i18next.d.ts`, and the locale JSON files
- The `nsSeparator` is `":"` (configured in `scanner.config.js`)
